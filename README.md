## 2. 从"面向字节"到"面向块"

磁盘不是内存, 它有两个不能回避的事实:

1. **读写的最小单位是块(512字节)**, 不是字节

2. **每次读写都很慢**(毫秒级, 比内存慢好几个数量级)

第1条决定了接口的形状: `block_read(blockno, buf, nblocks)`

第2条决定了必须有缓存

### 2.1 缓冲区缓存

假设要读一个文件的第100个字节:

```
   没有缓存:  读块 -> 取第 100 字节 -> 丢掉整块
              下次读第 101 字节 -> 又要读一次块 (磁盘: 再来一次)
```

同一块磁盘数据会被反复读取. 缓冲区缓存把最近用过的块留在内存里:

```
   bread(blockno):
       缓存里有  -> 直接返回, 并【增加引用计数】
       缓存里没有 -> 找一个空闲的缓存块, 读磁盘, 放进去, 返回
```

**引用计数**是这里最容易出错的地方:

- `bread` 返回时引用计数 +1, 表示"有人正在用这块数据"

- 用完必须 `brelse(b)`, 引用计数 -1

- 只有引用计数为0的缓存块才能被回收给别人用

忘记 `brelse` 的症状: **跑到第30次读磁盘时系统卡死**(缓存全被占满, `bread` 找不到可用块, 只好永远等下去). 这是本阶段最典型的bug

### 2.2 缓存的回收: LRU

缓存满了要挑一块扔出去. 策略是 **LRU(最近最少使用)**: 把刚刚用过的块移到链表头部, 回收时从**尾部**取——尾部的就是最久没被用过的

`bwrite(b)` 表示"这一块被我改过了, 请写回磁盘". 它和 `brelse(b)` 是两件事: **改过 ≠ 写完**

## 3. 位图: 哪些块是空闲的

磁盘上第一个块是**超级块**, 记录这台"磁盘文件系统"的全局信息:

```c
typedef struct superblock {
        uint32 magic;        /* 魔数: 用来确认"这确实是我们认识的磁盘" */
        uint32 size;         /* 总块数 */
        uint32 ninodes;      /* inode 总数 */
        uint32 inodestart;   /* inode 区从第几块开始 */
        uint32 nfiles;
} superblock_t;
```

紧接着是**位图**: 每一位表示一个数据块是空闲还是已用

```
   位图块:  1 0 0 1 1 1 0 0 ...
            │       │
            │       └── 第 3 块已用
            └── 第 0 块已用
```

`balloc()` 找第一个0并置1, `bfree()` 把对应位置0. 两个函数都必须**持有锁**——否则两个CPU可能同时找到同一个0

**一个容易忽略的细节**: 置位/清零时要处理"位在哪个字节、哪个bit". 用 `1u << (bit % 32)` 这类写法时要小心: 当 `bit` 达到32时, RISC-V的移位会按位宽取模, `1u << 32` 实际是 `1u << 0`——于是你改的是**完全不相干的那一位**, 而且没有任何报错

## 4. 磁盘镜像是怎么来的

QEMU启动时通过 `-drive` 挂载 `disk.img`. 这个镜像由宿主程序 `tools/mkfs/mkfs.c` 生成:

```
   mkfs disk.img user/test_1.elf
        │
        ├─ 写超级块 (魔数 / 块数 / inode 数)
        ├─ 清空位图, 把已用的块置 1
        ├─ 建立根目录
        └─ 把 test_1.elf 的内容写成一个文件
```

`mkfs` 用**宿主编译器**(`gcc`)编译, 不是交叉编译器——它跑在你的开发机上, 而不是开发板上

### 5.1 `block_read` / `block_write` 只是转发

它们取出默认块设备, 检查操作是否越界, 然后调用设备自己的 `ops`:

```c
int block_read(uint64 blockno, void *buf, uint32 nblocks)
{
        struct block_device *dev = block_default();
        if (!dev) return -1;
        if (blockno + nblocks > dev->nblocks) return -1;   /* 越界! */
        return dev->ops->read(dev, blockno, buf, nblocks);
}
```

**越界检查是必须的**: 块号是调用者给的, 越界读会读到别的设备/内存

### 5.2 `bread` 的核心是"引用计数 + LRU"

```
   1. 加锁遍历缓存
   2. 命中:  ref++, 移到链表头, 解锁, 返回
   3. 未命中: 找一个 ref==0 的缓存块 (从链表尾往前找)
              标记为"使用中", 解锁, 读磁盘 (读的时候不要持锁!)
              加锁, ref=1, 放进链表头, 返回
```

**读磁盘时不能持有缓存的锁**——那会让整个系统在磁盘I/O期间完全停下来

### 5.3 `balloc` / `bfree` 的边界

`balloc` 返回的块号必须在数据区范围内; `bfree` 要能处理"释放一个本来就不空闲的块"——这类不一致说明磁盘镜像被写坏了, 应当报错而不是静默接受

### 5.4 `virtio_rw` 是驱动里最容易写错的地方

VirtIO 用一种"描述符环 + 可用环 + 已用环"的协议和内核通信. 写错的典型症状是**请求发出去了但永远不完成**. 三个已经踩过的坑:

1. **queue 长度没有协商**: 设备说能放128个描述符, 但 `QUEUE_NUM` 必须设成你实际用的那个值(并且≤设备支持的最大值)

2. **`QUEUE_SEL` 在读 `QUEUE_NUM` 之前必须重新选一次**——读操作会改变内部游标

3. **`used.idx` 必须用 volatile 读**: 否则编译器会把循环里的读提到循环外, 表现为"加一句打印就能过"

最后一行就是**本阶段的验收标准**:

- 如果这几个字节不对, 说明**读回来的内容和磁盘上的不是一回事**(常见原因: 队列协商错了, 读到的是垃圾)

### 8.1 缓存策略与统计

**为什么值得做**：这一章的核心就是缓冲区缓存，但"LRU 到底好不好"只有数据能回答。
把策略做成可切换、把命中率打出来，你会第一次用**数字**评价一个内核设计选择，
也能亲眼看到"引用计数大于 0 的块不能被复用"这条不变式为什么必须存在。

**思路**：
- 先加统计：命中/未命中/淘汰次数/等待可复用块的次数，用一个 shell 命令打印
- 再做可切换策略：插入与淘汰的位置决定 LRU / FIFO；再加一个"随机替换"做对照
- 加法：**预读**——命中第 N 块时顺手把第 N+1 块读进来（顺序读的场景立刻见效）
- 注意两个坑：被引用的块不能被淘汰；预读会产生"还没人用"的块，
  要防止它们把缓存挤满导致"永远找不到可复用块"（本项目注释里正好记着这个坑）

**怎么算做到**：顺序遍历一个上百块的文件，LRU 与 FIFO 的命中率差异可解释；
开预读后未命中次数下降；缓存接近满时系统仍能正常工作（不卡死）。

**涉及**：`kernel/fs/bio.c`、`kernel/fs/block.c`、`kernel/lib/print.c`　**难度**：★★☆

### 8.2 MBR / GPT 分区表

**为什么值得做**：现在的磁盘镜像是"裸文件系统"——块 0 就是超级块。
真实磁盘上有分区表。这条改的是**磁盘格式契约**：镜像生成工具与内核必须同时改，
正好把"磁盘格式是跨程序契约"这件事变成一次真实体验（也解释了为什么格式要写死字节序与对齐）。

**思路**：
- 镜像侧：先在镜像头部写分区表，再把文件系统放进第一个分区
- 内核侧：在"块设备 → 文件系统"之间加一层很小的分区解析，
  得到"文件系统起始块 + 长度"，之后所有块号都加这个偏移
- 两种格式的差异要讲清：MBR 简单（一个扇区、4 个表项、小端）；
  GPT 复杂但更真实（主表 + 备份表、128 个表项、CRC32 校验、保护性 MBR）
- **不要动默认镜像布局**：用新的配置或新的镜像文件，否则本分支的期望输出会失效
- 签名与边界都要校验：分区表损坏时应明确报错，而不是被当成裸盘继续读

**怎么算做到**：能挂载"带分区的镜像"并列出同一批文件（可读性对照实验）；
故意破坏签名 → 明确报错；分区越界（起始+长度超过设备）被拒绝。

**涉及**：`tools/mkfs/mkfs.c`、`kernel/fs/block.c`、`include/kernel/block.h`、`configs/`（新增）　**难度**：★★★

### 8.3 异步 IO：写回与请求队列

**为什么值得做**：现在读写都是"发出去 → 原地轮询等完成"，
一次只等一块，等待期间 CPU 什么也做不了。真实内核把请求排进队列、由中断驱动完成，
发起者可以继续跑或睡下去——这是"阻塞式驱动"到"中断驱动"的关键一步，
也是 lab-6 的睡眠/唤醒在设备侧的第一个真实用途。

**思路**（两级，建议先做 L1）：
- **L1 延迟写（write-back）**：写操作只把块标成脏，真正落盘交给一个后台时机
  （空闲时、定时器里、或缓存不够时批量刷）；读时若碰到脏块直接用内存里的内容
- **L2 请求队列 + 中断驱动**：把请求挂进设备队列，发起者睡在"请求完成"事件上，
  设备中断里唤醒；驱动里那个"中断处理"的占位函数正是为此准备的
- 两个必须处理的竞态：**提交与完成之间**（先检查再睡，或用锁串起来——
  本项目在等待子进程那处就真实踩过"丢唤醒"）；**设备报错**要能唤醒等待者并带回错误码
- 别忘了多核：队列本身的互斥、以及"谁来发起下一次传输"

**怎么算做到**：L1 连续写多个块只触发一次批量刷盘（打印批大小）；
L2 请求期间进程处于睡眠（用 shell 看进程状态），中断到来后被唤醒且数据正确；
拔掉/停掉设备（模拟错误）时不卡死。

**涉及**：`kernel/fs/bio.c`、`kernel/fs/block.c`、`drivers/block/virtio_blk.c`、`kernel/proc/proc.c`　**难度**：★★★
