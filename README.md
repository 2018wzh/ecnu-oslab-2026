## 2. 文件描述符表 (kernel/fs/file.c)

本阶段需要在**kernel/fs/file.c**中补全文件描述符表, 核心是函数`fd_alloc`

它负责为进程分配一个空闲的文件描述符

**2.1 sys_open 的四个步骤**

`sys_open`需要按下面的顺序执行:

```
   1. uvm_copyin_str 把路径拷进内核 (PROC_NAME_MAX + 1 字节)
   2. inode_by_path 查找; 不存在且带 O_CREATE 时用
      inode_by_path_parent 拆出父目录 + 文件名, 再 inode_create
   3. file_alloc 分配 file 对象, 设置 readable / writable
   4. fd_alloc 拿一个 fd
```

任何一步失败都要回滚已经拿到的资源 (`inode_put` / `file_close`), 否则失败一次就泄漏一个 inode 引用, 反复失败会把 inode 缓存耗光

**2.2 sys_write 补上的那个分支**

`sys_write`已经写好了控制台路径, 你要补普通文件这一路:

```c
	if (f->type == FD_INODE) {
		int r = inode_write(f->ip, buf, (uint32)f->off, (uint32)n, 1);
		if (r > 0)
			f->off += (uint64)r;      /* 【别忘了推进偏移量】 */
		return (int64)r;
	}
```

注意最后一个参数是`1` (`is_user`), 告诉`inode_write`源地址是用户地址, 必须走`uvm_copyin`

**2.3 fd_alloc 的边界**

fd 表大小有限 (`NOFILE`), `fd_alloc`必须在表满时返回`E_NOFD`, 而不是越界写

另外 fd 0/1/2 通常已经被标准输入输出占用了

**2.4 sys_close 与 sys_lseek**

`sys_close`关闭一个已打开的文件, `sys_lseek`移动读/写指针的偏移量, 两者都通过 fd 查找到对应的 file 对象再操作

## 3. 加载并执行 ELF (kernel/proc/elf.c)

磁盘上的用户程序是以 ELF 格式存放的, 内核需要解析并加载它才能让用户程序真正跑起来

`elf.c`回答的是"ELF 文件格式长什么样", `proc/exec.c`回答的是"怎么切换地址空间并进入用户态", 两者拆开, 出问题时能立刻知道该看哪个文件

本阶段需要在**kernel/proc/elf.c**实现`exec_load`: 解析 ELF 头与程序头, 读取其中的 segment, 填充到用户堆区域, 返回程序入口地址

`sys_exec`在`sysfunc.c`中补齐: 从用户态拷入路径与参数, 调用`exec_load`, 构建新的地址空间, 切换页表并进入用户态

注意装载可能失败, 失败必须可恢复: 先造好整张新地址空间 (页表 + 段 + 栈), 再回收旧页面

## 4. 全系统整合

实现完成后, `init` 会 fork 出子进程, 子进程 `exec("/test_1")` 把映像换成磁盘上的 ELF (入口、段、权限全部来自那个文件), 跑完之后父进程 `wait` 回收它并拿到退出状态

前面所有阶段的工作 (页表、文件系统、块设备、trap、调度) 在这一刻被同时验证

### 4.1 PIE 程序加载（位置无关 + 相对重定位）

**为什么值得做**：现在用户程序链接在固定地址，内核按它写死的虚拟地址原样映射。
PIE（位置无关可执行文件）允许加载到任意基址——它是地址空间随机化、
共享库、"同一个程序被多次以不同基址加载"的前提，也是"链接器与加载器之间的契约"
最集中的一块知识。

**思路**：
- 构建侧：用户程序改成按位置无关的方式编译，并**保留重定位表**
  （注意现在打了 strip，会把重定位表一起剥掉，要改）
- 内核侧：对这类可执行文件先选一个加载基址（偏移量），
  所有段按"基址 + 段虚拟地址"映射，入口 = 基址 + 文件头里的入口
- 然后处理重定位：从动态段里找到重定位表的位置/大小/表项大小，
  逐项处理"相对重定位"（把"基址 + 加数"写到指定位置）；
  RISC-V 上先只支持最常见的那一种就够
- 两个坑：重定位表在**用户地址空间里**，必须经页表读写，不能直接解引用内核指针；
  重定位必须在"段都映射好之后、进入用户态之前"完成，`.bss` 部分也要覆盖到

**怎么算做到**：同一个程序连续两次加载到**不同基址**都能跑通（打印自己的入口地址）；
故意不处理重定位表 → 程序在非零基址上崩（反证重定位是必需的）。

**涉及**：`kernel/proc/elf.c`、`kernel/syscall/sysfunc.c`、`user/arch/riscv64/user.ld.in`、`mk/build.mk`　**难度**：★★★

### 4.2 第二套文件系统（读得懂"别人的"镜像）

**为什么值得做**：现在只有一套自制格式，"文件系统"看起来只有一种做法。
去做一套**别人做的**镜像（例如 FAT 只读）会立刻暴露：哪些是我们的假设、
哪些才是文件系统的普遍概念。它也是上一章那套文件系统抽象最自然的用途——
如果加一套文件系统要改路径解析，说明抽象没抽干净。

**思路**：
- 只做**只读**：解析引导参数（每扇区字节数、簇大小、FAT 表位置、根目录位置），
  按 FAT 链遍历簇，读目录项（先支持短名——8 字符主名 + 3 字符扩展名——就够，长名是加分）
- 用统一的文件系统接口把它挂到某个目录（例如 `/mnt/fat`），让路径解析自动支持它
- 测试数据要真实：用宿主机的工具或下载一个 FAT 镜像，而不是自己写一个
  "像 FAT 的东西"——只有真的镜像才能证明你读对了
- **不要做写支持**：FAT 的写路径涉及两份 FAT 同步与目录项分配，工作量翻倍且容易把镜像写坏；
  写操作明确返回"只读文件系统"错误即可
- 注意簇与扇区的换算、FAT 表项的位宽差异（12/16/32 位），以及链上的环检测

**怎么算做到**：能列出真实 FAT 镜像里的文件并读出内容（与宿主机上看到的一致）；
写入被明确拒绝；损坏的 FAT 链（成环/越界）不会让内核死循环。

**涉及**：`include/kernel/fs.h`（接口）、`kernel/fs/`（新增一套实现）、`kernel/fs/fs.c`（挂载）　**难度**：★★★

### 4.3 procfs：把内核状态变成可读文件

**为什么值得做**：现在想看内核状态只能靠打印和 shell 命令；procfs 把这套**诊断能力**
变成用户程序也能读的接口（`cat /proc/ticks`）。它同时是"文件系统接口被非文件用途复用"
的经典案例——正好检验上一章那套抽象够不够通用（一个没有磁盘、内容按需生成的文件系统）。

**思路**：
- 做一套"内存文件系统"，每个文件的内容由一个**回调函数按需生成**，
  而不是静态数据：tick 数、进程表文本、内存统计、挂载列表
- 挂到 `/proc`，用户程序 `open/read/close` 就能打印内核状态
- 三个语义要想清楚：**读是流式的**（要支持偏移量：重复读要么从头、要么接着上次）；
  **长度**（能先算出来最好，算不出来就要定义"读到结尾"的行为）；**只读**
  （写操作返回明确错误）
- 内容格式保持简单稳定（一行一条、字段固定），这样用户程序可以用它做断言——
  procfs 一旦稳定，它就是你自己的"验收工具"

**怎么算做到**：用户程序连续两次读 `/proc/ticks`，值在增长；
读 `/proc/procs` 能列出当前所有进程（含 idle）；对 procfs 的写操作返回只读错误；
挂载列表里能看到 `/proc`。

**涉及**：`kernel/fs/`（新增一套实现）、`kernel/fs/fs.c`（挂载）、`kernel/proc/proc.c`（导出进程表文本）　**难度**：★★☆
