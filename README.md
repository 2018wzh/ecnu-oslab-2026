# LAB-6: 单进程走向多进程——进程调度与生命周期

**前言**

经过前几个实验, 系统里第一次真正有了**多个**可运行实体

启动流程自己变成一个进程, 每个CPU有一个idle进程, 时钟中断会抢占当前进程

进程可以fork、睡眠、唤醒、退出并被回收

本实验主要围绕两个主题: 进程调度 + 生命周期

## 2. idle进程

调度器的职责是"选一个可运行的进程运行"。如果一个都没有呢?

```
   所有进程都在等待 I/O / 时钟
              ↓
   调度器找不到任何可运行的进程
              ↓
   如果没有 idle: 只能 panic 或者死循环 (而且死循环还占着 CPU)
```

所以每个CPU都要有一个**永远不会退出、永远可运行**的idle进程

它只有一件事可做:

```c
while (1)
        asm volatile("wfi");   /* 等中断 —— 不烧 CPU */
```

`wfi`(wait for interrupt)让CPU停下来直到有中断

下一次时钟中断到来时, 调度器会重新挑一个进程运行

**注意 idle 的 id 是 0, 而第一个"真正的"用户进程 `init` 是 pid 1**

## 3. 进程状态机

```
                    proc_alloc
                        │
                        ▼
   PROC_UNUSED ─────► PROC_RUNNABLE ◄────────┐
                        │  ▲                 │ wakeup
              被调度器选中 │  │ 被抢占        │
                        ▼  │                 │
                    PROC_RUNNING ────► PROC_SLEEPING
                        │  sleep
                        │ exit
                        ▼
                    PROC_ZOMBIE ──── wait ────► PROC_UNUSED
```

- **ZOMBIE 不能立刻消失**: 父进程还要通过 `wait` 拿到它的退出码, 所以进程块必须留到那一刻
- **父进程先死怎么办**: 把子进程"过继"给别的进程(reparent), 否则它们永远等不到 `wait`, 成为孤儿僵尸
- **`proc_free` 必须逐页归还**: 内核栈、trapframe所在的页、整个用户地址空间(`uvm_free`)

## 4. 上下文切换在保存什么

```c
arch_context_switch(struct arch_context *old, struct arch_context *new);
```

它只保存**callee-saved 寄存器**: `ra, sp, s0-s11`

为什么不存全部寄存器? 因为这是 **S-mode 内部**的切换, 发生在一次普通的函数调用里

按照 RISC-V ABI, 调用者已经把 caller-saved 寄存器保存在自己的栈帧里了, `arch_context_switch` 只要保证"返回后 callee-saved 寄存器的值不变"就履行了 ABI 义务

对比 `trapframe`: 那是 **U-mode → S-mode** 的切换, 用户程序假定"什么都没发生过", 所以必须保存全部32个寄存器

`arch_context_switch` 还有一个反直觉的性质: **它"返回两次"**. 第一次是正常返回; 将来别人切回 `old` 时, 从 `old->ra` 恢复再 `ret`, 于是又回到当初那个调用点之后. 这就是 `fork` 能"一次调用、两次返回"的机制基础

## 5. lost wakeup

```c
proc_sleep(chan, lk);     /* 睡在 chan 上, 并释放 lk */
proc_wakeup(chan);        /* 唤醒所有睡在 chan 上的人 */
```

错误写法:

```c
if (condition_not_met)
        proc_sleep(chan, lk);       /* ✗ 在"判断"和"睡下"之间有窗口 */
```

问题在于: 从"判断条件"到"真正睡下"之间有一段窗口. 另一个CPU完全可能在这个窗口里改变条件并调用`proc_wakeup`, 那个wakeup发现进程还在RUNNING, 于是**什么也不做**. 然后本进程才真正睡下去, 于是**永远醒不过来**

正确做法: 调用者持有保护条件的锁 `lk`, 在**持有锁的情况下**调用 `proc_sleep`, 由 `proc_sleep` 内部**原子地**完成"设置状态 + 释放锁":

```
   1. 拿 p->lk
   2. 设置 p->chan 与 p->state = SLEEPING
   3. 【此时才释放调用者的锁 lk】   ← 顺序是关键
   4. sched_switch()
   5. 被唤醒后: 清 chan, 释放 p->lk, 重新获取 lk
```

**第 3 步的顺序反了就会 lost wakeup**: 如果先释放 `lk` 再设 `state = SLEEPING`, `wakeup` 会看到 RUNNING 而不唤醒

## 6. 具体任务

### 6.1 先读已经写好的 `proc_yield`

`kernel/proc/proc.c` 里的 `proc_yield()` 已经写好了:

```c
void proc_yield(void)
{
        sched_switch();
}
```

它是你实现 `proc_sleep` / `proc_exit` 时的参照, 所有"让出CPU"的路径最后都落到 `sched_switch`

### 6.2 `pick_next` 的策略

遍历进程表, 挑一个 `PROC_RUNNABLE` 的进程. **先挑"不是本CPU正在运行的"那个**, 否则你会"切换到自己", 那等于什么都没做

如果遍历不到任何可运行进程, 就返回本CPU的idle进程, 这就是"无路可退时的退路"

### 6.3 `proc_copy`(fork) 的四步

1. 分配新的进程控制块和内核栈
2. **逐页真实拷贝用户内存**(不能只复制页表项! 只复制页表项会让父子共享同一物理页, 写一个会影响另一个, 那不是fork而是线程)
3. 复制trapframe, 但把子进程的 `a0` 改成 0
4. 继承已打开的文件: **共享file对象**(引用计数+1)

### 6.4 `proc_exit` 的顺序

```
   1. 关闭所有打开的文件
   2. 唤醒父进程 (如果它在 wait)
   3. 把自己的子进程过继给别人
   4. 释放用户地址空间 (uvm_free)
   5. state = ZOMBIE, 然后 sched_switch()   ← 永不返回
```

**第 5 步必须在最后**: 先让出CPU, 后面的清理代码就永远不会执行了

### 6.1 睡眠与超时队列

**为什么值得做**：现在"睡眠/唤醒"只能等别人叫醒，没有任何"睡一段时间"的能力——
而 `timer.h` 里那个"等若干 tick"的接口声明了很久，一直没人实现。
真实内核用一个按键（到期时刻）排序的队列管理所有定时等待，它同时是 6.3 tickless 的前置。

**思路**：
- 维护一张"到期时刻 → 进程"的有序表（升序链表足够，小根堆是加分）；
  "睡 n 个 tick" = 记下"当前时刻 + n"，然后睡在一个专用通道上
- 时钟中断里检查队首是否到期并唤醒；进程被别的事件提前唤醒时要从队列里**摘掉**，
  否则会留下"过期的等待者"（症状是莫名被唤醒一次）
- 说清时间语义：接口收的是**绝对时刻**还是"间隔"？驱动层的设置接口收的是绝对时刻，
  这一点要利用好，避免"过了的时刻再设一次"这种 bug
- 被终止或退出的进程要能从队列里清理干净

**怎么算做到**：多个进程按到期顺序被唤醒（打印各自睡了多少 tick）；
提前唤醒之后队列长度回到 0；唤醒时刻误差在一个 tick 内。

**涉及**：`kernel/trap/timer.c`、`include/kernel/timer.h`、`kernel/proc/proc.c`　**难度**：★★☆

### 6.2 可切换的调度策略

**为什么值得做**：这一章的设计要点是"机制与策略分离"，而 `pick_next` 就是那个策略点。
"可切换策略"是检验这句话是否真的成立的最直接方式——如果换策略要动 `sched_switch`，
说明分离没做到。它也很容易产出一份有数据的实验报告。

**思路**：
- 定义一个很小的策略接口：一个"选下一个"的函数 + 一个"时钟到来时"的回调
  （用于时间片计数、优先级老化等），再写 2–3 个实现：
  简单轮转、时间片可调、优先级、乃至"空闲核去偷一个就绪进程"
- 用 shell 命令在运行期切换（lab-3 的内核 shell 在这里第二次发挥作用），
  并打印每个进程的"被调度次数/等待时长"做对照
- 边界想清楚：状态迁移（就绪/运行/睡眠）属于**机制**，不能跟着策略走；
  时间片计数放"机制侧"还是"策略侧"要先决定（建议回调只做计数，选择只做选择）
- 多核别忘了：两个 CPU 同时"选"必须互斥（本项目用一把调度器全局锁解决）

**怎么算做到**：切换策略只用改策略表、不动 `sched_switch`；
两种策略下每个可用进程都能被跑到（无饿死）；对照数据能解释差异。

**涉及**：`kernel/sched/sched.c`、`include/kernel/proc.h`、`kernel/init/main.c`（选策略）　**难度**：★★★

### 6.3 完整 tickless：让下一次中断跟着事件走

**为什么值得做**：lab-3 做到了"动态间隔"，但间隔还是拍脑袋定的。
真正的 tickless 是"下一次中断 = 最近一个到期事件"（超时队列的队首、当前进程时间片到期），
空闲且无事件时干脆不设。它把"时钟"从"心跳"变成"闹钟"，也是移动设备省电的根本原因。

**思路**：
- 在一个函数里算出"下一个事件时刻"：队列队首到期时刻、当前进程时间片到期时刻，取最小
- 在几个关键位置调用它：调度切换之后、进程睡下去之后、时钟中断返回前
- 空闲且队列为空时不再设置中断（等外部中断唤醒），需要时再设
- 时间源精度决定最小间隔；如果 tick 计数与"真实时间"绑得太死，考虑改成时间戳
- 最经典的坑：**忘了设置下一次中断 → 系统永远不再被唤醒**。调试期用一个命令打印
  "现在时刻 / 下次中断时刻 / 队首到期时刻"，一眼就能看出漏设

**怎么算做到**：空闲（无进程可跑、无定时等待）时中断计数停止增长；
有定时等待时唤醒误差在一个 tick 内；系统长时间运行不会卡死。

**涉及**：`kernel/sched/sched.c`、`kernel/trap/timer.c`、`kernel/trap/trap.c`　**难度**：★★★
