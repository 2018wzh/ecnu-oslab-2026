## 任务1：系统调用流程建立

用户程序通过`ecall`进入内核, 触发trap, 由`trap_user_handler`根据scause
分类处理

系统调用到来时, 调用`trap_handle_syscall`进行分派跳转, 由`sys_func`
根据系统调用编号调用具体的处理函数, 组成一条规范的系统调用流程

随后, 你需要补全`sys_read`系统调用。对照已经写好的`sys_write`: 取
`myproc()`校验pgtbl, 用`fd_get`拿file对象并检查它可读, 当`FD_CONSOLE`时
用`console_getc()`取一个字符, 再用`uvm_copyout`写回用户缓冲区, 返回实际
读到的字节数

**注意: `sys_read`用的是`uvm_copyout`(内核 -> 用户), 而`sys_write`用的是
`uvm_copyin`(用户 -> 内核), 方向别写反——写反了编译不会报错, 但用户会拿到
垃圾数据**

## 任务2：用户态和内核态的数据迁移

系统调用参数存放在寄存器中, 其中地址类参数指向用户地址空间。用户传入的
地址基于用户页表, 而进入内核后使用的是内核页表, 两者并不匹配

解决这个问题需要手动查询用户页表, 找到虚拟地址对应的物理地址, 之后再做
数据迁移

需要提醒的是: 内核绝不能直接解引用用户传来的指针, 理由有两条:

- 用户指针可能根本没有映射, 内核态直接读会触发缺页、导致整个系统崩溃

- 用户指针可能指向内核内存, 借此读写内核数据结构构成提权漏洞

因此每一次访问都必须经过页表校验。本阶段提供一组唯一的入口函数:

```c
uvm_copyin     (pgtbl, dst_kva, src_va, len)   用户 -> 内核
uvm_copyout    (pgtbl, dst_va,  src_kva, len)  内核 -> 用户
uvm_copyin_str (pgtbl, dst, src_va, max)       用户 -> 内核 (字符串)
```

`uvm_copyin_str`有三处需要留意:

1. **逐字节拷贝**: 长度由用户数据决定, 不能先算长度再拷贝 (那要遍历两次)

2. **必须有上限**: 用户传一个永远遇不到`'\0'`的缓冲区, 内核就会一路读到
   别的内存里去, `max`是硬性护栏

3. **超长要返回错误**, 而不是"尽力而为"

请你完成`kernel/mm/uvm.c`中的`uvm_copyin_str`和`uvm_free`。`uvm_free`在
进程退出时把用过的物理页逐页归还给分配器, 但**只归还用户页面**, 内核映射
是从内核页表复制来的共享项, 绝不能归还, 否则下一次分配会把内核自己的页
发出去

## 任务3：用户堆与栈的管理

### 堆的管理是手动的

**堆-HEAP**为用户提供一块连续的大范围内存空间, 它的生长方向是低地址到
高地址。内核提供`sys_brk`系统调用, 允许用户改变堆顶的位置。`sys_brk`的
效果进一步分为:

- 空间增加: `old_heap_top < new_heap_top`

- 空间减少: `old_heap_top > new_heap_top`

- 空间不变: `old_heap_top == new_heap_top`

- 查询当前堆顶: `new_heap_top == 0`

涉及内存页面的申请释放、用户页表的修改、`proc->heap_top`的更新。请你完成
`sys_brk`、`uvm_heap_grow`、`uvm_heap_ungrow`

### 栈的管理是自动的

**栈-STACK**为用户的临时变量和函数执行提供了一块连续的内存空间, 它的生长
方向是高地址到低地址。用户程序无需显式地管理栈空间, 由内核根据用户需要
自动管理

内核不会在进程初始化时直接分配一个很大的栈空间, 而是根据程序运行的需要
逐步分配足够大的空间。当用户读或写一块未分配的地址空间时, 会触发**13号
异常(Load Page Fault)** / **15号异常(Store/AMO Page Fault)**, 我们在
`trap_user_handler`里识别这两种异常, 然后调用`uvm_ustack_grow`来处理缺页
异常: 首先判断发生page fault的地址 (放在stval寄存器) 是否是合理的栈扩展
地址, 确认合法性后申请物理页面、修改用户页表、更新`proc->ustack_npage`。
一次可以扩展多个页面, 扩展后不会发生收缩 (和堆的管理不同)

需要提醒的是:

- 增长的粒度是页: `len`不是页的整数倍时, 要向上取整到页边界

- 栈增长必须设上下界: `fault`不能离已有栈太远, 也不能越过`USER_STACK_BASE`

### 边界检查

需要提醒的是: 我们在栈和堆的中间区域里, 划分了一段地址空间作为离散内存
空间的区域 (mmap区域), 它的起点地址被定义为`MMAP_BEGIN`, 终点被定义为
`MMAP_END`, 因此栈的生长不应该越过`MMAP_END`, 堆的生长不应该越过
`MMAP_BEGIN`

## 任务4：mmap 与 munmap

应用程序有时需要临时申请一块内存空间, 过一会就释放掉。本阶段用链表结构
维护离散的内存资源:`mmap_region_t`描述一块连续地址空间, 它起始于`begin`,
包括`npages`个页面, 进程在地址空间中记录第一个资源节点, 各个节点通过
`next`指针串联成立单链表

内核规定可以提供`N_MMAP`个`mmap_region_t`结构体资源, 为保证各个进程可以
高效有序地共享这种资源, 在内核里维护一个资源仓库, 通过自旋锁确保任何时刻
只有一个进程在获取或释放资源

从系统调用出发, 梳理mmap的逻辑过程:

- 用户程序发出`sys_mmap(begin, len)`申请一块内存空间

- 调用`uvm_mmap(begin, npages, w)`在`begin`建立一段映射, `begin == 0`
  表示由内核选地址

- `uvm_mmap`首先创建一个新的`mmap_region_t`来描述这块新的地址空间, 随后
  把它插入进程mmap链表的合适位置 (保持整体有序), 新插入的节点可能和前后
  节点相邻或同时相邻, 考虑到仓库资源受限, 应将相邻节点尽可能合并

- 合并完成后, 进行物理页申请和页表修改的步骤

`uvm_munmap(begin, npages)`解除一段映射并回收其物理页, 整体流程与mmap相近。

需要提醒的是: mmap的地址必须避开已映射区, 在C版中请为进程结构体
`proc_t`增加mmap相关的起始记录, 内核选地址时从专门的mmap基址往下/往上
找空洞, 完成`uvm_mmap`与`uvm_munmap`

### 6.1 mmap：让用户自己申请内存

**为什么值得做**：现在用户地址空间只有两段：代码/数据一段、固定大小的用户栈一段。
`mmap` 让用户程序能自己申请内存（堆、共享缓冲，"把文件映射进地址空间"的前置）。
系统调用表里**只有这一个被标着"（扩展）"**：位置和语义都给你留好了，
返回映射的起始地址——这是一条"照着 ABI 把缺口补上"的进阶目标。

**思路**：
- 校验先行：长度是否页对齐、是否超过上限、请求区间是否与既有映射重叠、
  是否落在用户地址范围内
- 分配与映射用既有接口组合：拿到物理页 → 映射到用户页表 → 返回虚拟地址
- 地址参数为 0 时表示"内核挑一个地址"：建议在高地址区从下往上或从上往下找空洞
- **必须记下"哪些地址是 mmap 出来的"**（一张很小的区间表）。否则 lab-6 的 fork
  不知道该拷哪些页、进程退出时不知道该回收哪些页——这一条是后面几章的前提

**怎么算做到**：测试程序 mmap 一段、写入、读回都正确；越界访问触发缺页而不是静默写到别的页；
空闲页数在 mmap 后减少、退出后回到基线。

**涉及**：`kernel/syscall/sysfunc.c`、`kernel/syscall/syscall.c`（分发）、`include/uapi/syscall.h`、`kernel/mm/uvmmap.c`　**难度**：★★☆

### 6.2 用户栈与堆的增长

**为什么值得做**：现在用户栈是固定大小（写满就撞到未映射区，缺页直接把进程干掉）。
真实内核对栈是"按需向下增长"的；堆则是"向上增长的第二个区间"。
这条让你第一次面对"缺页不是错误，而是'该给页了'的信号"。

**思路**：
- 在用户态缺页处理里区分两种情况：故障地址**落在允许增长的栈区**（在栈底附近、
  且没有超过增长上限）→ 分配一页、记下新的栈底、返回用户态重试；
  其它地址 → 视为非法访问，按"用户程序出错"处理（而不是内核崩）
- 判断依据是**故障地址**，不是触发指令的地址——这是缺页处理最容易搞错的一点
- 一定要设增长上限（否则等于给了用户一把无限增长的刀），并在超限时给出明确错误
- 堆可以用一个"设置堆顶"的系统调用，或者直接用 6.1 的 mmap + 懒分配实现
- 缺页发生在陷阱上下文里：分配失败要能体面地失败，不能死循环重试同一条指令

**怎么算做到**：一个递归很深、或在栈上开大数组的测试程序能跑过原来会崩的深度；
超过上限时进程被明确终止并打印原因，内核不受影响。

**涉及**：`arch/riscv64/trap/trap.c`（用户态陷阱分发）、`kernel/mm/uvmmap.c`、`kernel/mm/uvm.c`　**难度**：★★★

### 6.3 统一地址空间管理与 lazy-alloc

**为什么值得做**：6.1 的 mmap 是"立刻给页"，6.2 的栈增长是"缺页时给页"——
两件事本质相同却各写一遍。真实内核用**一张区间表（VMA）+ 页表**描述地址空间：
申请时只登记区间，真正访问时才给页（lazy）。这张表也是 lab-6 的进程复制、
lab-7/8 的文件映射的共同地基。

**思路**：
- 定义"区间"：起始、长度、权限、类型（代码/数据/栈/mmap/文件映射），
  用一张有序表挂在进程上（先做线性数组即可，几十项足够）
- 把三处入口统一到这张表上：mmap 只登记、栈增长往表里更新栈底、
  缺页处理统一"查表 → 决定给页还是报错"
- 分配失败必须能回退（内存耗尽时杀掉进程而不是死循环）；
  同一条指令可能反复触发缺页，重试必须幂等
- 为 lab-6 预留：**进程复制 = 复制这张表 + 复制页内容**（先做全量拷贝）

**怎么算做到**：mmap 之后空闲页数不变，访问第一页之后才减少；
访问第 3 页只多分配 1 页（用打印统计验证）；超出任何区间的访问仍然被拒；
`proc` 相关打印里能看到这个进程的区间表。

**涉及**：`kernel/mm/uvmmap.c`、`kernel/mm/uvm.c`、`include/kernel/proc.h`、`arch/riscv64/trap/trap.c`　**难度**：★★★
