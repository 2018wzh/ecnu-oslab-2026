# LAB-2: 内存管理初步

**前言**

在lab-1中, 我们学习了机器启动流程、UART设备驱动、格式化输出和自旋锁

完成lab-1后, OS内核已经可以启动、打印, 但对内存的态度是"拿来就用": 代码里写0x80200000, CPU就去访问物理地址0x80200000

在lab-2中, 我们开始认识和管理"程序除了CPU外最常访问的共享资源——内存"

内存管理不是一步到位的, lab-2主要关注物理内存和内核态虚拟内存, 剩余部分将在后面的实验逐渐完善

本阶段要引入两件事:

```
   物理内存分配器   ——  "哪些页是空闲的, 我要一页"
   Sv39 页表        ——  "这个虚拟地址对应哪个物理地址"
```

然后在最后打开分页(往satp写页表地址)。从那一刻起, 内核里每一行代码访问的地址都要先经过页表翻译

## 第一阶段: 物理内存

物理内存按照地址空间划分为几个部分:

```
   PLAT_DRAM_BASE
        │
        ├── 固件 (OpenSBI) 占用的部分          <- 分配器必须跳过
        │
        ├── 内核代码 + 数据 (.text/.rodata/.data/.bss)
        │
        └── 空闲内存  <-- 分配器管理的部分
```

`pmem_init()` 要做的是: 算出"哪些页是空闲的", 并把它们串成一条链表

一页是4096字节, 而链表只需要存"下一页的地址"(8字节)。所以最自然的做法是**把next指针直接写在那一页的开头**:

```
   空闲页 A         空闲页 B         空闲页 C
   ┌────────┐      ┌────────┐      ┌────────┐
   │ &B     │  ->  │ &C     │  ->  │ NULL   │
   │  (空)  │      │  (空)  │      │  (空)  │
   └────────┘      └────────┘      └────────┘
```

内存管理器的元数据不需要单独的空间——空闲的内存本身就可以用来存它。代价是"分配出去之后元数据就没了", 而那正好是我们要的(被分配的页不该再带链表信息)

分配器要注意两个边界:

1. **固件占用的区域不能分配**。OpenSBI 仍然驻留在内存里, 如果把它当成空闲页分配出去, 下一次内核调用 SBI(比如打印)就会踩坏固件——现象是"打印了几行之后突然崩溃"
2. **分配器自己也要从空闲页里拿内存吗**? 不需要——空闲链表是静态的头指针 + 页面内的next指针, 没有额外的动态结构

## 第二阶段: Sv39 页表

通过"地址"可以区分每个4KB物理页, 但为了方便编程, 我们给应用程序提供"独占内存资源"的幻觉。为此引入**虚拟内存**: 建立一个表格, 记录虚拟地址到物理地址的对应关系, 并通过MMU自动完成翻译

虚拟内存的构建围绕两个核心概念: **页表项(PTE)** 和 **页表(pgtbl)**。页表是由页表项构成的, 一个页表项对应一个物理页

### 二级/三级页表结构

Sv39 用 **39 位**虚拟地址, 拆成三段各9位, 加上页内12位偏移:

```
   38        30 29        21 20        12 11              0
   ┌───────────┬───────────┬───────────┬─────────────────┐
   │  VPN[2]   │  VPN[1]   │  VPN[0]   │    页内偏移      │
   │  9 位     │  9 位     │  9 位     │    12 位         │
   └───────────┴───────────┴───────────┴─────────────────┘
         │           │           │
         └─ 一级 ────┴─ 二级 ────┴─ 三级 -> 4 KiB 页
```

三级下来正好覆盖39位。能从**顶级页表**的PTE里获得**次级页表**所在物理页的页号和标志位, 依此类推, 直到**低级页表**的PTE里获得真正存储数据和代码的一般物理页

页表项里的关键位:

| 位 | 名字 | 含义 |
|---|---|---|
| 0 | V | 有效——为0时这一项不存在 |
| 1 | R | 可读 |
| 2 | W | 可写 |
| 3 | X | 可执行 |
| 4 | U | 用户态可访问 |
| 6 | A | 曾被访问过 |
| 7 | D | 曾被写过 |

**R/W/X 全为 0 表示这是一个"指向下一级页表的指针", 不是叶子。** 同一张表里既有"到下一级的链接", 也有"最终映射", 靠R/W/X区分

**A/D 位必须显式置上。** 有些实现不会自动置位, 如果不置, 第一次访问会触发缺页——而本阶段还没有缺页处理, 现象就是内核停住

### 实现要点

**kernel/mm/vm.c** 中的 `walk` 与 `kvm_map` 推荐按照以下顺序实现。

注意 `walk` 的两种用法: `alloc=false` 只查不改(用于翻译), `alloc=true` 需要沿途建表。写下标时很容易把方向写反——遍历顺序与地址位的顺序是**相反**的: 根用VPN[2], 叶子用VPN[0]。调试方法: 把根表项的下标算出来, 对着地址的高9位验证一次

页表所在的页也在物理内存里。如果页表**没有映射自己所在的区域**, 那么CPU在读第二级/第三级页表时就会缺页。这在恒等映射下是成立的(因为整个内核区都映射了), 但如果你的映射范围算漏了一段, 现象会是"刚写完satp就崩"

## 第三阶段: 内核页表与打开分页

完成基本的页表操作函数后, 我们需要给内核页表 **kernel_pgtbl** 设置映射关系并为每个CPU启用它

`kvm_init()` 与 `kvm_init_hart()` 是分开的:

```
  kvm_init()       建立页表结构, 往里面填映射
                   此时 CPU 还在用物理地址 —— 出错了容易调试

  kvm_init_hart()  把页表地址写进 satp, 刷新 TLB
                   从这一条指令之后, 所有访问都经过页表
```

分两步的价值在于: 建表过程中的bug不会与"切换后的bug"混在一起。如果合成一步, 一个映射写错了, 你看到的现象是"切换之后立刻崩", 而无法判断是"表没建对"还是"切换方式不对"

打开分页后, **设备 MMIO 地址也要能在新页表里访问到**, 否则串口会在切换的瞬间失效。这就是 `platform_map_devices()` 存在的原因。它所在的位置由平台决定, 因为"这台机器有哪些设备、在什么地址"是机器的事实

本内核把内核空间映射成**恒等映射**(虚拟地址 == 物理地址)。好处是切换前后行为一致, 不需要 trampoline 那一套技巧。代价是"看起来什么都没变", 因此这个阶段特别容易出问题却看不出来——所以测试节"确认分页已开启"的输出非常重要

映射完毕后把 **kernel_pgtbl** 写入 **satp** 寄存器, 正式开启 **MMU** 翻译。之后的内存访问本质都是访问虚拟地址, 经过页表和MMU的协作被自动翻译为物理地址

### 9.1 buddy 分配器

**为什么值得做**：现在的空闲页链表只能一页一页给，回答不了"我要连续 8 页"。
而页表、DMA 缓冲、大页都需要**物理连续**的块。buddy 是这个问题最经典、也最适合教学的回答：
它把"外部碎片"变成可以观察、可以证明的现象。

**思路**：
- 按 order 维护多条空闲链表（4KB、8KB、16KB……）：分配 order n 时若该级为空，
  就向上一级要一块、切一半，另一半挂到下一级
- 释放时找**伙伴**：伙伴地址 = 本块地址异或"块大小"；伙伴空闲就合并，逐级向上
- 需要一个"每页状态"数组来判断伙伴是空闲还是已分配（放在内核保留页里即可）
- **接口兼容**：先让 buddy 实现现有的"按页分配/释放"语义（lab-5、lab-6 都在用），
  再另外提供带 order 的版本

**怎么算做到**：分配/释放计数守恒；反复分配 128 个 4 页块再全部释放后，
仍能分配一个 512 页的连续块；故意释放未分配的块或重复释放能被明确抓住。

**涉及**：`kernel/mm/pmem.c`、`include/kernel/mm.h`　**难度**：★★☆

### 9.2 内核堆（kmalloc / kfree）

**为什么值得做**：内核里的小对象（进程控制块、缓冲区头、路径缓冲）现在要么静态数组、
要么整页分配。有了内核堆，后面几章的表就能按需增长，它也是 slab 的前置。
"内核里的动态内存"和"用户堆"完全是两件事，值得亲手做一次。

**思路**：
- L1 简单 free-list：按大小分档（8/16/32/…/2048 字节），每档一条空闲链表，
  从整页里切分；大块直接走整页分配
- L2 slab：为"同类对象"建专用缓存（对象大小固定），后面进程表与缓冲区缓存都能受益
- 三个必须想清楚的点：**堆的页从哪来**（把新物理页映射进内核地址空间）、
  **对齐**（至少满足最大对齐，设备 DMA 可能要求更高）、
  **失败路径**（分配 0 字节、内存耗尽时返回什么、调用者怎么回滚）

**怎么算做到**：1 到 4096 字节各种大小都能分配、写满、释放、再分配且不重叠
（用固定模式填充验证）；释放后空闲页数回到基线；越界写能被哨兵或断言抓到。

**涉及**：`kernel/mm/`（新增文件）、`include/kernel/mm.h`、`kernel/mm/vm.c`　**难度**：★★☆

### 9.3 大页支持（2MB 超级页）

**为什么值得做**：Sv39 的中间级页表项可以**直接当叶子**用，一个项映射 2MB。
这既减少页表页数与 TLB 压力，也是"页表粒度可选"最直观的教材——
而"中间级也能是叶子"正是页表遍历代码最容易写错的地方。

**思路**：
- 映射时先判断：虚拟地址、物理地址、长度是否都按 2MB 对齐？是就在中间级写叶子项
- 遍历（翻译）代码必须能识别"中间级就是叶子"，否则会把物理页号当成下一级页表去读，
  症状是"某些地址翻译出乱七八糟的结果"
- 撤销映射、权限检查同样要处理"叶子出现在两级"的情况
- 拿内核镜像或一段 DRAM 做对照：同一段内存分别用 4KB 页与 2MB 页映射，比较页表页数量

**怎么算做到**：一段 4MB 内存用两个大页映射成功；抽查首/中/尾地址翻译都正确；
页表页数统计下降；故意把非对齐地址按大页映射时给出明确错误。

**涉及**：`arch/riscv64/mm/pgtable.c`、`kernel/mm/vm.c`、`kernel/mm/kvmmap.c`　**难度**：★★★
