# ECNU OSLab ABI 规范

> 本文件定义 **用户态与内核之间的接口契约**。
> C 版本（`ecnu-oslab-2026`）与 Rust 版本（`ecnu-oslab-2026-rs`）**必须同时遵守它**，
> 这样两套实现才可以跑同一组用户程序、用同一套测试验证。

## 为什么需要一份独立的 ABI 规范

分析报告里有一条重要原则：

> 共享的应当是 **规范、ABI、测试用例、磁盘格式**，
> 而不是内核实现本身。

具体到本课程：

```
                  ┌──────────────────────┐
                  │   本文件 (ABI 规范)   │
                  └──────────┬───────────┘
                             │
          ┌──────────────────┴──────────────────┐
          │                                     │
   ┌──────▼──────┐                      ┌───────▼──────┐
   │  C 内核      │                      │  Rust 内核    │
   │  Makefile    │                      │  cargo xtask │
   └─────────────┘                      └──────────────┘
          │                                     │
          └──────────────────┬──────────────────┘
                             │
                  ┌──────────▼───────────┐
                  │  同一组用户程序/测试   │
                  └──────────────────────┘
```

**不要通过 FFI 共享调度器、页表或文件系统实现。** 那会让学生把时间花在
理解语言绑定上，而不是"用两种语言各自实现一个内核"。共享规范、各自实现，
才是这个双仓库设计想要训练的能力。

## 1. 系统调用调用约定

### 寄存器约定（RISC-V，与 Linux 一致）

| 寄存器 | 用途 |
|---|---|
| `a7` | 系统调用号 |
| `a0`–`a5` | 参数（最多 6 个） |
| `a0` | **返回值**（负数表示错误） |
| `ecall` | 触发陷入 |

### 调用序列

```asm
li   a7, <syscall_number>
li   a0, <arg0>
li   a1, <arg1>
ecall                    # 陷入 S-mode
# 返回后 a0 = 结果或负错误码
```

### 内核侧必须遵守的三条

1. **从 trapframe 读取参数**，不要把用户寄存器当函数参数。
2. **返回前把结果写回 trapframe 的 `a0`**。
3. **`sepc += 4`** —— `ecall` 返回时 `sepc` 指向 `ecall` 本身，
   不推进就会无限重复执行同一条指令。

## 2. 系统调用表

| 号 | 名称 | 参数 | 返回 | 引入 lab |
|---|---|---|---|---|
| 1 | `exit` | `status` | 不返回 | 5 |
| 2 | `fork` | — | 父进程得子 pid，子进程得 0 | 5 |
| 3 | `read` | `fd, buf, n` | 读到的字节数，0 = EOF，负数 = 错误 | 9 |
| 4 | `write` | `fd, buf, n` | 写入的字节数，负数 = 错误 | 4 |
| 5 | `exec` | `path, argv` | 成功不返回，失败返回负错误码 | 9 |
| 6 | `wait` | `status` | 子进程 pid，-1 = 无子进程 | 6 |
| 9 | `mmap` | `addr, len, prot` | 映射起始地址 | (扩展) |
| 10 | `getpid` | — | 当前进程号 | 5 |
| 11 | `open` | `path, flags, mode` | 文件描述符，负数 = 错误 | 9 |
| 12 | `close` | `fd` | 0 成功 | 9 |
| 13 | `lseek` | `fd, offset, whence` | 新偏移量 | 9 |

`SYS_MAX = 14`。**未实现的系统调用必须返回负错误码，不能返回 0 假装成功** ——
后者会让用户程序的错误被掩盖，比直接失败更难排查。

具体分两种情况，**不能混为一谈**：

| 情况 | 返回 | 含义 |
|---|---|---|
| 号在 ABI 里有定义，但内核还没实现（目前只有 `mmap`） | `-38` (`E_NOSYS`) | "这条路还没铺" —— 换个做法或等后续阶段 |
| 号在 ABI 里根本不存在 | `-1` (`E_BADARG`) | "你的调用号写错了" —— 查自己的程序 |

两者都用负数，但排查方向完全相反：看到 `-1` 要去查参数/调用号，看到 `-38`
说明内核确实还没实现这个功能。C 版与 Rust 版必须给出同样的错误码。

### 参数语义

| 参数 | 类型 | 说明 |
|---|---|---|
| `fd` | 有符号整数 | `0`/`1`/`2` 固定为 stdin/stdout/stderr |
| `buf` | **用户虚拟地址** | 内核**必须**经 `uvm_copyin/copyout` 校验 |
| `n` | 无符号整数 | 字节数；过大时应拒绝（防止内存耗尽） |
| `path` | **用户虚拟地址** | 以 `\0` 结尾的字符串，须先拷入内核 |
| `flags` | 位掩码 | 见下表 |
| `whence` | 整数 | `0`=SET, `1`=CUR, `2`=END |

### `open` 的 flags

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | `O_RDONLY` | 只读 |
| 1 | `O_WRONLY` | 只写 |
| 2 | `O_RDWR` | 读写 |
| 4 | `O_CREATE` | 不存在则创建 |

## 3. 错误码

全部为负数。**内核不得因用户传入非法参数而崩溃** —— 应返回错误码。

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | `E_OK` | 成功 |
| -1 | `E_BADARG` | 参数非法（指针越界、fd 越界、长度过大等） |
| -2 | `E_NOENT` | 文件或目录不存在 |
| -3 | `E_NOMEM` | 内存不足 |
| -4 | `E_IO` | 设备或磁盘 I/O 错误 |
| -5 | `E_NOFD` | 文件描述符无效或已用尽 |
| -6 | `E_BADFMT` | 可执行文件格式错误 |

## 4. 进程语义

### `fork` 的两次返回

| 进程 | `a0` 的值 |
|---|---|
| 父进程 | 子进程 pid（> 0） |
| 子进程 | `0` |

子进程的地址空间是父进程的**副本**（不是共享）。实现要点：
复制 `trapframe` 后把子进程的 `a0` 置 0。

### `fork` 后的文件描述符

子进程**继承**父进程已打开的 fd，且父子**共享同一个 file 对象**
（因此共享读写偏移量）—— 与 Linux 语义一致。

### `exec` 不创建新进程

它**替换当前进程**的地址空间。成功即不返回；失败才返回错误码。

### 预置的 fd

任何进入用户态的进程都必须先装好：

| fd | 设备 |
|---|---|
| 0 | stdin（控制台输入） |
| 1 | stdout（控制台输出） |
| 2 | stderr（控制台输出，可加前缀） |

**缺少这三项的症状很有欺骗性**：进程正常运行、正常退出，但你**看不到任何输出**，
因为 `write(1, ...)` 返回了 `E_NOFD` 而用户程序通常不检查返回值。

## 5. 磁盘文件系统格式

C 与 Rust 版本共用同一种镜像格式，由 `tools/mkfs` 生成，两边内核都要能读。

### 块与布局

```
块大小: 512 字节, 小端序

块 0            : 超级块
块 1            : 空闲位图 (每个 bit 表示一个块)
块 2 .. 2+INODEBLKS-1 : inode 区
之后            : 数据区
```

### 超级块（块 0，偏移以字节计）

| 偏移 | 宽度 | 字段 |
|---|---|---|
| 0 | 4 | `magic` = `0x10203040` |
| 4 | 4 | `size`（总块数） |
| 8 | 4 | `ninodes` |
| 12 | 4 | `inodestart`（inode 区起始块号） |
| 16 | 4 | 保留（日志区大小，本课程为 0） |
| 20 | 4 | `nfiles`（根目录下的文件数） |

### inode（64 字节，**紧凑无填充**）

| 偏移 | 宽度 | 字段 |
|---|---|---|
| 0 | 2 | `type`：0=空闲, 1=目录, 2=文件, 3=设备 |
| 2 | 2 | `major`（设备号） |
| 4 | 2 | `minor` |
| 6 | 2 | `nlink`（硬链接数） |
| 8 | 4 | `size`（字节） |
| 12 | 4×13 | `addrs[13]`：前 12 个直接块，第 13 个是一级间接块 |

**inode 号是 1-based**，数组下标是 0-based。换算必须显式减 1 ——
这个 off-by-one 会导致"超级块正常但 inode 全是垃圾"。

单文件上限：`12×512 + 128×512 = 70 KB`（`128 = 512/4`）。

### 目录项（16 字节）

| 偏移 | 宽度 | 字段 |
|---|---|---|
| 0 | 2 | `inum`（0 = 该项空闲） |
| 2 | 14 | `name`（定长，**不保证以 `\0` 结尾**） |

因为不保证结尾符，比较名字**必须**用 `strncmp(name, de.name, 14)`。

### ⚠️ 关于结构体内存布局

**不要把宿主程序的结构体直接 `fwrite` 到磁盘。** 结构体的内存布局受
编译器、对齐规则和架构影响（`sizeof` 可能是 64 也可能是 68 或 72）。

正确做法（两边都这么做）：
- 生成端：**逐字段按字节序写入**（见 `tools/mkfs/mkfs.c` 的 `put16`/`put32`）
- 内核端：结构体加 `packed`（C）或 `#[repr(C, packed)]`（Rust），
  并加**编译期断言**检查大小正好是 64

## 6. 可执行文件格式

| | 内核内嵌的 initcode | 磁盘上的用户程序 |
|---|---|---|
| 格式 | **扁平二进制**（无头部） | **ELF64** |
| 加载地址 | 编译期固定（`0x1000`） | 由程序头表决定 |
| 为什么 | 加载极简单，无需解析器 | 需要灵活的段布局与权限 |

**initcode 的链接地址必须等于加载地址**：它使用 PC 相对寻址，
两者不一致会导致所有地址偏移（症状：取指缺页 at `0x0`）。

ELF 要求：
- 魔数 `0x7F 'E' 'L' 'F'`
- `e_machine = 243`（RISC-V）—— **必须校验**，否则加载异构架构程序会随机跑飞
- 只加载 `PT_LOAD` 段
- 段权限映射：`PF_X`→可执行, `PF_W`→可写, `PF_R`→可读，**并加用户可访问位**
- `filesz` 用于拷贝，`memsz` 用于决定映射大小（差值为 `.bss`，须为 0）

## 7. 两个版本的一致性检查清单

修改任一实现后，请确认：

- [ ] 系统调用号与本文件一致
- [ ] 错误码符号与数值一致
- [ ] `fork` 的两次返回值语义一致
- [ ] 磁盘镜像可以互换（用 A 生成的镜像，B 能读）
- [ ] 同一个用户程序在两个内核上都能运行
- [ ] 两者的 `uvm_copyin/copyout` 都做了用户指针校验

最后两条是"真的实现了同一份 ABI"的最终证据。
