# 实验工作流

> 本课程沿用 2025 的分支模型：**每个 lab 一个分支，逐个合并推进。**
> 2026 增加了一条硬性要求：**每个 lab 都必须在 QEMU 与 VisionFive2
> 两个平台上通过。**

---

## 1. 分支模型

本仓库有 9 个分支, **逐级建立在彼此之上**:

```
lab-1   启动与打印
  │
lab-2   加上物理内存与页表
  │
  ...
lab-9   加上文件系统与 ELF 加载
```

每个分支 `lab-N` 上你会看到三样东西:

| 你看到的 | 含义 |
|---|---|
| **lab-1 .. lab-N 的框架** | 头文件、构建规则、`main()` 的骨架、每个函数上方的说明注释 |
| **所有任务函数的空函数体** | `lab-1` 到 `lab-N` 的任务都留成 `{ }`, 等你实现 |
| **lab-(N+1) 及之后的源文件** | 在代码里**根本不存在** —— 那些文件不在这个分支上 |

**注意最后一行**: 后面的子系统不是"被注释掉"或"被开关关掉", 而是这个
分支上就没有这些文件。所以你不必面对整个内核, 每个阶段只看得到自己
需要理解的那部分。

`lab-N` 的 README 里有本阶段要完成的函数清单 (按阶段标注), 以及每个
函数要做什么、怎么验证。

### 做完一个 lab 之后怎么进入下一个

```bash
git merge lab-4          # 例: 从 lab-3 进入 lab-4
```

它带来的是**下一阶段的框架**: 新增的源文件、长出来的头文件、`main()`
里新加的那一步初始化。你在上一个 lab 里自己写好的函数体**不会被覆盖** ——
因为两个分支上那些函数体本来就是空的 (空的与空的相同, 不是冲突)。

> **只看本阶段框架涉及的文件。** 不属于本阶段的文件 (尤其是 `main.c`
> 这类每个阶段都不同的文件) 不要改, 否则下次合并一定冲突。

## 2. 完整操作流程

### 第一步：准备仓库

```bash
git clone <课程仓库地址> my-oslab
cd my-oslab

# 建立你自己的实验分支
git checkout -b my-work lab-1
```

> **不要直接在 `lab-N` 分支上改**。`lab-N` 是课程提供的骨架，
> 助教可能更新它（修 bug、改进讲解）。

### 第二步：做第一个 lab

```bash
# 1. 读本 lab 的指导书 (代码组织结构 -> 概念讲解 -> 测试)
cat README.md

# 2. 按指导书的清单找到需要实现的空函数, 逐个实现

# 3. 验证两个平台
make CONFIG=riscv64-qemu-virt-sbi run
make CONFIG=riscv64-visionfive2-uboot image

# 4. 提交
git add -A
git commit -m "lab-1: 实现自旋锁与串口输出"
```

### 第三步：进入下一个 lab

```bash
git merge lab-2          # 把 lab-2 的骨架合并进来
cat README.md            # 读 lab-2 的指导书
# …… 实现空函数, 双平台验证, 提交 ……
```

### 第四步：重复直到 lab-9

每一个 lab 都是同一套动作：
**merge 下一个分支 → 读 README → 实现空函数 → 双平台验证 → 提交**。

## 3. 每个 lab 的验收标准

**一个 lab 是否算通过，唯一标准是两个平台都要过。**

| 检查项 | 命令 | 通过标准 |
|---|---|---|
| QEMU 构建 | `make CONFIG=riscv64-qemu-virt-sbi build` | 输出"构建成功" |
| QEMU 运行 | `make CONFIG=riscv64-qemu-virt-sbi run` | 达到本 lab 的预期输出 |
| VF2 构建 | `make CONFIG=riscv64-visionfive2-uboot build` | 输出"构建成功" |
| VF2 镜像 | `make CONFIG=riscv64-visionfive2-uboot image` | 生成 `kernel.itb` |
| 链接地址 | `riscv64-elf-nm build/*/kernel.elf \| grep ' _entry$'` | QEMU=0x80200000, VF2=0x40200000 |
| 编译告警 | 上面两条 build 的输出 | **一条 warning 都没有** |

如果你有开发板，再加上：

| 检查项 | 通过标准 |
|---|---|
| 真机启动 | 串口看到本 lab 的预期输出 |

## 4. 为什么"两个平台都要过"是硬要求

这不是为了增加工作量，而是因为**只在一个平台上通过，会隐藏掉大量真实 bug**。
下面这些是本项目在开发过程中真实遇到过的、只在某一个平台上暴露的问题：

| 问题 | 只在哪个平台暴露 | 症状 |
|---|---|---|
| hart 区间写错 | VF2（hart 0 是监控核） | 4 核只起来 3 个，无任何报错 |
| 串口输入时钟与分频不匹配 | VF2（24MHz vs QEMU 10MHz） | 输出乱码 |
| 中断号写死成 `1 << irq` | VF2（UART0 是 irq 32） | RISC-V 移位按位宽取模，实际打开了 irq 0 |
| 页表漏映射设备区 | 两者都可能，但地址不同 | 开分页后串口突然无输出 |
| 链接地址与加载地址不一致 | VF2（U-Boot 按 FIT 搬运） | 一进去就跑飞，无输出 |
| VirtIO 用的是 legacy 还是 modern | QEMU（实际是 legacy v1） | 请求发出但永不完成 |
| SD 卡控制器与 VirtIO 接口差异 | VF2 | 文件系统读不出数据 |

**如果你只在 QEMU 上验证**，上表中一半以上的问题你永远不会遇到 ——
而它们恰恰是"操作系统工程师的日常工作"。

## 5. 关于真机（没有开发板怎么办）

你**不需要**有开发板才能完成本课程。要求是：

1. `make CONFIG=riscv64-visionfive2-uboot image` 能成功生成 FIT 镜像
2. 用 `dtc` 验证镜像结构正确：

```bash
dtc -I dtb -O dts build/riscv64-visionfive2-uboot/kernel.itb
```

应当看到 `arch = "riscv"`、`load = <0x40200000>`、`entry = <0x40200000>`。

3. 在实验报告里说明：**你的实现中有哪些地方是平台相关的？
   为什么它们被放在了 `platform/` 而不是 `kernel/`？**

这个说明比"我在真机上跑通了"更能体现你理解了本次改造的重点。

## 6. 常见问题

**Q: 我 merge 的时候冲突了怎么办？**
A: 大概率是因为你改了 `lab-N` 里"已经实现好"的代码（那些不属于你要做的部分）。
   如果是某个你上一轮实现过的文件，建议接受 lab 分支那一侧的内容。

**Q: 我能不能不用分支，直接在一个分支上从头写到尾？**
A: 可以，但强烈不建议。分支模型的价值是：每个 lab 都有一个
   "已知正确的起点"，出问题时可以快速定位是自己的实现错了还是环境问题。

**Q: 我能看到"标准答案"吗？**
A: 这个仓库里没有标准答案：每个分支都只有框架与空函数体。
   遇到想不通的地方, 可以对照本分支 README 的说明, 以及你在上一个
   分支里自己实现过、并且已经理解了的代码。

**Q: 助教会看我怎么写代码，还是只看最终能不能跑？**
A: 都看。特别是：
   - 你有没有把平台相关的东西放进 `kernel/`
   - 你有没有在两个平台都验证
   - 你的实验报告里对"为什么这样分层"的理解

## 7. 提交物清单

每个 lab 的提交应当包含：

- [ ] 代码实现（在 `my-work` 分支上）
- [ ] QEMU 运行日志（证明达到了本 lab 目标）
- [ ] VF2 的 FIT 镜像结构输出（`dtc` 的结果）
- [ ] 简短说明：**本 lab 你改了哪些文件？有没有碰到必须改 `kernel/` 的情况？**

最后一项是本课程最想看到的内容。
